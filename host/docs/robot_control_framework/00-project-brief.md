# 项目章程

## 问题与目标

现有仓库已经能够把 HPM 固件、SOEM、ROS 2、CAN 电机、IMU、电源板和手柄组合起来，但设备映射、协议分支、实时循环、ROS 接口和诊断数据的边界仍然分散。新增一个设备往往需要同时改静态数组、协议 switch、PDO 结构、ROS 消息和启动脚本，难以证明时序和故障行为。

本框架的目标是提供一个可在 Ubuntu 上长期运行的机器人控制底座：

- 对硬实时控制给出可测量的周期、抖动、总线负载和内存预算；
- 对 ROS 2 提供标准、可组合、可录制和可调试的控制/传感接口；
- 通过版本化设备描述和协议插件减少新增设备的改动面；
- 在 DDS、ROS 节点、网络或应用崩溃时仍能执行本地安全策略；
- 让每个故障都能从 ROS 命令追踪到 IPC、周期、线缆帧和反馈。

## 目标用户与核心流程

| 用户 | 主要流程 | 可观察结果 |
| --- | --- | --- |
| 控制算法工程师 | 发布轨迹/速度目标，读取标准状态 | 不需要知道 CAN ID 或私有帧；可用 `ros2_control` 控制器和 rosbag 回放 |
| 驱动工程师 | 接入新协议、执行器或传感器 | 描述文件、codec、driver、测试夹具和诊断项有固定清单 |
| 现场工程师 | 启停、标定、复位、升级和排障 | `robotctl`、诊断状态、指标和故障 trace 能给出明确原因 |
| 安全/发布负责人 | 审核停机、版本、回滚和证据 | 有状态机、故障注入记录、性能门槛和可追溯配置指纹 |

核心端到端流程：

```text
任务/遥控目标
  -> ROS 2 命令校验与 authority lease
  -> robot_control / ros2_control
  -> 固定大小 IPC（sequence/deadline/crc）
  -> robot_rt 周期：读总线 -> 解码 -> 控制/安全 -> 编码 -> 写总线
  -> 执行器；反馈沿同一 trace/sequence 回传
```

## 本期范围（必须）

- EtherCAT、CAN/CAN-FD、UART/RS-485、普通 Ethernet/UDP 等总线的统一边界；先保留现有 HPM/SOEM、MCAN、YESENSE、PowerLink 适配器。
- 执行器（位置/速度/力矩/使能/故障）和传感器（样本时间、坐标系、质量位、校准）的统一设备模型。
- 版本化协议规范、纯 codec、设备 profile、注册与兼容矩阵。
- `robot_rt` 与 ROS 2 的有界 IPC、命令仲裁、生命周期、看门狗和安全状态机。
- `ros2_control` 硬件 facade、标准消息/QoS、诊断/指标/trace/录包。
- 仿真、回环、HIL、性能、故障注入和发布回滚流程。

## 明确不做

- 不把 ROS 2/DDS 作为安全闭环或现场总线；不承诺网络断开时还能继续接收运动命令。
- 不在本阶段自研 DDS、通用 RPC、数据库、可视化平台或全新的 EtherCAT 主站。
- 不把任意第三方共享库从 ROS 参数动态加载到实时线程。
- 不替代硬件急停、STO、限位、独立电源保护或法规认证；软件设计只提供系统级配合和证据。
- 不一次性重写现有固件/ROS 包；先用兼容适配器和影子运行迁移。

## 首版质量预算（暂定，需实测确认）

| 指标 | 首版目标 | 测量条件 |
| --- | ---: | --- |
| 本地 RT 周期 | 1 kHz（可配置 250 Hz--2 kHz） | PREEMPT_RT、目标板、额定设备数 |
| 周期执行时间 | p99.9 < 800 us，单次不得超过 950 us | 包含读、解码、安全、写 |
| 周期抖动 | p99.9 <= 50 us，最大 <= 100 us | 以单调时钟/硬件 Sync0 记录 |
| RT CPU | 独占核平均 < 70%，峰值 < 85% | 1 小时额定负载 |
| CAN 总线占用 | admission 上限 70% | 按真实位填充、仲裁和重发计算 |
| 反馈新鲜度 | 执行器依赖的反馈 age <= 2 个周期 | stale 时进入定义的降级状态 |
| ROS 命令 | 本机入 RT p99 < 10 ms | 跨主机只下发目标/轨迹，不走 1 kHz |
| 内存 | 启动后 RT 堆使用不增长 | 运行 1 小时、故障注入期间 |
| 安全响应 | 由硬件/RT 看门狗定义并实测 | ROS/DDS 断开、进程崩溃、总线断线 |

这些数字是容量计划的起点，不是“最佳性能”承诺。任何设备 profile 合入前都必须用自己的帧数、周期和 WCET 重新计算。

## 约束、假设与未决项

### 已知事实

- 当前固件以 FreeRTOS 运行 EtherCAT、motor、IMU、status 任务；host `GatewayEcat` 已有独立 1 kHz SOEM 线程和固定大小快照。
- 当前 ROS 2 工作区包含 `hpm_gateway_control`、`hpm_gateway_power`、`hpm_gateway_gamepad` 和 `hpm_gateway_msgs`；PowerLink Python 串口属于非实时域。
- 当前 PDO/电机映射仍有静态轴号、CAN 总线和协议约束；MCAN 当前使用非阻塞 TX FIFO，但队列满载、重试和丢帧语义仍需单独测量和固化。

### 暂定假设

- 生产主机以 Ubuntu 24.04 + ROS 2 Jazzy 为新基线，Ubuntu 22.04/Humble 通过兼容 profile 维持过渡期支持。
- 一台机器人默认单机运行 `robot_rt` 与 `robot_control`；多机通过高层 ROS 2/网关连接，硬实时闭环留在本机。
- 硬件提供独立急停/STO或电源切断输入；若没有，发布前必须补齐硬件保护，而不能用 ROS 服务代替。

### 必须在 M0 确认

- 目标机器人轴数、每轴协议/帧数/周期、CAN 位速率、EtherCAT DC/拓扑和传感器峰值带宽。
- 需要的安全完整性等级、急停响应时间和电源/驱动器的硬件能力；软件文档不替代安全认证。
- RDK/TROS 是否强制 Fast DDS、是否允许 PREEMPT_RT、是否允许 `CAP_NET_RAW/CAP_SYS_NICE/CAP_IPC_LOCK`。
- SOEM GPLv3/商业双授权的产品许可证路径，或替代 EtherCAT 后端。
