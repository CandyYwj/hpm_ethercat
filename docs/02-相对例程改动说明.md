# 相对例程改动说明

本工程不是直接把某一个 HPM 例程拿来编过，而是在多个例程基础上重新拼成了一个网关工程。最重要的参照物是：

- `hpm_app/software/apps/tsn_simplest_switch`
- `hpm_app/software/apps/tsn_static_mac_switch`
- `hpm_app/software/apps/tsn_dynamic_mac_switch`

下面按模块说明相对例程做了什么改动。

## 1. 从“交换机例程”改成“网关工程”

原始 TSN 例程的目标主要是：

- 收到一个包后直接转发。
- 做静态 MAC 表或动态 MAC 学习。
- 演示端口速率切换和交换机行为。

本工程的目标完全不同：

- TSN 侧收到的不再直接交换转发，而是要写进 EtherCAT PDO。
- EtherCAT 侧收到的 PDO 也不再进入示例数字 IO，而是要封装成以太网帧发出去。

因此这里不是“改了几个参数”，而是把数据面的核心职责从“交换”改成了“协议桥接”。

## 2. 新增了 EtherCAT 从站层

这是相对 TSN 例程最大的结构性变化。

新增内容：

- 引入 SSC 对象字典和应用层回调。
- 引入 `APPL_InputMapping()` / `APPL_OutputMapping()`。
- 使用 `MainInit()` + `MainLoop()` 管理 ESM 状态机和 PDO 同步。
- 把原始 60 字节双向数据定义成 EtherCAT PDO。

关键文件：

- `firmware/ecat_tsn_gateway/application/gateway_app.c`
- `firmware/ecat_tsn_gateway/SSC/Src/digital_ioObjects.h`
- `firmware/ecat_tsn_gateway/SSC/ESI/ECAT_IO.xml`
- `firmware/ecat_tsn_gateway/SSC/Config/HPM_ECAT_IO_Config.xml`
- `firmware/ecat_tsn_gateway/SSC/Src/eeprom.h`

## 3. 把 PDO 定义改成了 60 字节双向网关缓冲区

标准数字 IO 例程通常是 bit/word 级的离散量映射，本工程改成了面向报文的块数据映射。

当前映射思路：

- 输入区 `0x6000 ~ 0x6003`
- 输出区 `0x7010 ~ 0x7013`
- 每个对象 15 字节
- 4 个对象拼成 60 字节

这么做的原因：

- SSC 这套对象定义更适合用多个 `OCTET_STRING[15]` 拼装。
- 既能满足 60 字节固定帧，又能让 XML/ESI/EEPROM 保持一致。

## 4. 新增了桥接层，而不是让 SSC 直接碰 TSN

本工程刻意把 SSC 回调和 TSN 驱动隔开，中间加了一层桥接缓冲。

新增的桥接抽象：

- `g_pdo_output_buf`
- `g_pdo_input_buf`
- `g_pdo_output_updated`
- `g_pdo_input_updated`
- `gateway_bridge_poll()`
- `gateway_tsn_rx_isr()`

这样分层的好处：

1. `gateway_app.c` 只负责 SSC 视角的数据搬运。
2. `gateway_bridge.c` 只负责协议转换和 DMA/TSW 细节。
3. 后续改协议，不需要把 EtherCAT 和 TSW 逻辑混在一个函数里改。

## 5. TSN 接收路径从“例程回环/学习”改成“过滤 + 入环形队列”

相对 `tsn_static_mac_switch` / `tsn_dynamic_mac_switch`，这里的 RX 路径改成：

1. IRQ 中从 DMA 取回 frame。
2. 检查 EtherType 是否为 `0x88B5`。
3. 学习 Jetson 源 MAC。
4. 把帧压入 `g_jetson_to_rdk_ring`。
5. 在主循环 `gateway_bridge_poll()` 中出队并写入 PDO 输入缓冲区。

这样做的原因：

- IRQ 里不适合做太重的协议处理。
- EtherCAT 主循环和 TSN IRQ 的速率不同，需要一个解耦缓冲。

## 6. TSN 发送路径做了几个关键补丁

这是整个工程里最关键的一批改动。

### 6.1 增加了合法的 TSW 发送头

不能只把裸以太网帧交给 DMA。当前实现会先在 `g_tsn_tx_buf` 头部构造 `tx_hdr_desc_t`：

- `dest_port = tsw_cpu_send_to_port_1`
- `queue = tsw_traffic_queue_0`

这一步是让 TSW 知道这帧要从哪个端口发出去。

### 6.2 强制以太网帧最小长度 60 字节

以太网最小帧长度不足时，当前代码会补零到 60 字节。

否则某些小 payload 会在链路侧表现异常。

### 6.3 从“盲发”改成“带返回状态检查的发送”

当前使用：

```c
tsw_send_frame_check_response(...)
```

而不是只提交 DMA 后不看结果。

这样可以把 `stat`、`MM2S_DMA_SR`、失败次数都打印出来，定位 DMA/端口问题。

### 6.4 显式初始化 MM2S 发送 DMA

这是最终打通 `ECAT -> TSN` 的关键修复之一。

新增逻辑：

- `tsw_get_default_dma_config(&dma_config);`
- `tsw_init_send(BOARD_TSN, &dma_config);`

如果没有这一步，之前已经验证过会出现持续发送失败。

## 7. 参考 full-port 例程，强制端口工作在 1000M

TSN 例程中本来有大量通过按键切换 10M/100M/1000M 的代码。网关工程没有保留按键切换，而是直接抽取出稳定配置路径：

- MDIO 写 `0x1140`
- `full_port_tsn_general_config(...1000mbps...)`
- `full_port_tsn_ep_mac_config(...tsw_mac_mode_gmii...)`

改动原因：

- 网关工程需要开机即可稳定通信，不适合等人工按键切换端口模式。
- 实测这是让 `port1` 稳定发包的必要前置条件之一。

## 8. 增加了 Jetson MAC 学习机制

这部分既参考了动态 MAC 学习例程，又做了简化。

区别在于：

- 不是维护一个完整动态 MAC 转发表。
- 当前只重点维护“Jetson 这一端”的返回地址。
- 第一次收到 Jetson 来包后，用源 MAC 更新 `lookup_table(1)`。

这让 `ECAT -> TSN` 能把包准确发回最近一次通信的 Jetson 网卡。

## 9. EtherCAT 主站相对普通 SOEM 用法也做了定制

`host/rdk_ecat_master/ecat_gateway_test.c` 不是简单的 SOEM 扫描样例，关键改动有：

### 9.1 严格按真实状态检查从站状态

- 加了 `EC_STATE_BASIC_MASK`
- 用 `ecx_statecheck()` 返回值做掩码判断

避免“代码里把状态写成 OP，但设备实际上没到 OP”的假阳性。

### 9.2 SAFE-OP 到 OP 期间持续发 PDO

新增 `wait_for_op_with_pdo()`：

- 先写一次 PDO
- 请求 OP
- 在等待 OP 的循环里不断 `send_processdata()` / `receive_processdata()`

这是 EtherCAT 侧的另一个关键修复。没有这个动作，从站可能始终等不到有效输出。

### 9.3 用户消息改成每周期发送

之前实现里只每 100 个周期发一次真实数据，其余发心跳。现在改成：

- 有用户消息时，每周期都发 `DATA`
- 没有用户消息时，才发 `HEARTBEAT`

这样更符合“网关测试程序”的直觉，也更容易观察 Jetson 收包。

## 10. 增加了大量针对联调的调试信息

当前工程里的调试打印不是装饰，而是把很多“看不见的状态”显式化了：

- 固件 `SSC: ...`
- `APPL_StartOutputHandler called`
- `APPL_OutputMapping #n called`
- `ECAT->TSN #n`
- `TSN->ECAT #n`
- `Learned Jetson MAC: ...`

这些打印让定位问题时可以快速判断故障在哪一层：

- 没到 OP
- PDO 没触发
- TSW 发包失败
- Jetson MAC 没学到
- TSN 包到了但没进 PDO

## 11. 可以把整个工程理解成两类改造的叠加

### 第一类：把 TSN 例程改造成可控的数据面

- 端口固定初始化
- RX/TX DMA 显式配置
- lookup table 定制
- CPU 收发路径可控

### 第二类：把 SSC 数字 IO 示例改造成报文型从站

- 60 字节双向 PDO
- 网关头定义
- APPL 回调定制
- SOEM 主站测试程序配套

真正打通，是这两类改动同时成立的结果。
