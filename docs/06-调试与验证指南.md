# 调试与验证指南

本文总结当前工程联调时最有价值的现象、日志和排查顺序。

## 1. 最小验证矩阵

建议分三步验证，不要一上来三端一起跑。

### 1.1 先验证 EtherCAT 从站能进 OP

在 RDK 侧运行：

```bash
sudo ./ecat_gateway_test eth0 "hello"
```

关键观察点：

- 能扫到 1 个从站
- Vendor/Product 正确
- `PRE-OP` 成功
- `SAFE-OP` 成功
- `OP` 成功

如果到不了 `OP`，先不要看 Jetson。

### 1.2 再验证 RDK -> Jetson

Jetson 侧运行：

```bash
sudo ./receive_from_board eth0
```

RDK 侧运行：

```bash
sudo ./ecat_gateway_test eth0 "hello"
```

正常现象：

- 固件有 `APPL_OutputMapping`
- 固件有 `ECAT->TSN #n`
- Jetson 收到 `Payload: "hello"`

### 1.3 最后验证 Jetson -> RDK

RDK 侧先运行主站，确保已经进入：

- `Cyclic exchange started.`

然后 Jetson 侧发包：

```bash
sudo ./send_to_board eth0 "Hello RDK"
```

正常现象：

- 固件打印 `Learned Jetson MAC`
- 固件打印 `TSN->ECAT #1: type=01 len=...`
- RDK 打印 `[FROM_JETSON] ... payload="Hello RDK"`

## 2. 固件侧日志怎么看

## 2.1 `ESC hardware OK`

说明 ESC 硬件初始化成功。

如果没有这句，说明还没到 SSC 层。

## 2.2 `PDO: 60 bytes in, 60 bytes out`

说明当前 SSC 对象字典和映射计算结果正确。

如果这里不是 60/60，而你以为自己定义的是 60/60，说明对象字典或映射元数据不一致。

## 2.3 `Gateway running`

说明主循环已经开始执行。

## 2.4 `APPL_StartOutputHandler called`

说明 EtherCAT 主站已经开始把输出真正送到从站应用层。

这通常意味着：

- 从站已经接近或进入 OP
- 主站 PDO 正在实际驱动

## 2.5 `APPL_OutputMapping #n called`

说明输出 PDO 已经进入 `APPL_OutputMapping()`。

如果你看不到这句，问题一般在：

- 主站没到 OP
- 主站没持续发 PDO
- PDO 映射不一致

## 2.6 `SSC: ...`

这是最有信息量的一条周期性状态打印。

重点字段：

- `al`
  - EtherCAT AL 状态
  - `01` 常见于 `INIT`
  - `08` 表示 `OP`
- `out`
  - 输出处理是否在跑
- `1stOut`
  - 是否收到过第一帧主站输出
- `E2T`
  - `ECAT -> TSN` 成功计数
- `T2E`
  - `TSN -> ECAT` 成功计数
- `TXF`
  - TSN 发送失败次数
- `txst`
  - 最近一次发送返回状态
- `mm2s`
  - 发送 DMA 状态寄存器
- `phy0/phy1`
  - PHY BMCR/BMSR 读数

经验判断：

- `al=08` 且 `out=1`，说明 EtherCAT 这边基本正常。
- `E2T` 增长，说明 `RDK -> Jetson` 正常。
- `T2E` 增长，说明 `Jetson -> RDK` 已经进了 PDO 输入缓冲。
- `TXF` 增长，说明 TSW 发包路径仍有问题。

## 3. Jetson 侧日志怎么看

## 3.1 `send_to_board`

关键输出：

- Interface
- Source MAC
- Target MAC
- Message
- `Sent xx bytes OK`

这只能说明“Linux 原始 socket 发出去了”，不能说明 HPM 一定收到了。

### 3.2 `receive_from_board`

如果收到：

- `Type: DATA`
- `Payload: "hello"`

则说明：

- RDK 输出 PDO 正常
- HPM `ECAT -> TSN` 正常
- TSW port1 正常

## 4. RDK 侧日志怎么看

## 4.1 状态切换阶段

关键输出：

- `Slave 1 state 0x02 OK`
- `Slave 1 state 0x04 OK`
- `Slave 1 state 0x08 OK`

分别对应：

- `PRE-OP`
- `SAFE-OP`
- `OP`

## 4.2 运行阶段

关键输出：

- `Cyclic exchange started.`

只有看到这句后，RDK 才真正开始周期性：

- 收输入 PDO
- 打印 Jetson 来的数据
- 发输出 PDO

## 5. 为什么 Jetson 发了，RDK 有时不打印

当前实现里，这是一个很重要的时序问题。

可能出现的顺序：

1. Jetson 先发包。
2. HPM 已经收到了，日志里有 `TSN->ECAT`。
3. `APPL_InputMapping()` 把这条消息送进 ESC 输入区并清掉更新标志。
4. 此时 RDK 打印线程还没开始，或者还没进入下一次读取。
5. 后续用户看到“板子收到了，但 RDK 没打印”。

这不是链路不通，而是当前实现的输入 PDO 采用了一次消费模型。

最稳的操作顺序是：

1. 先启动固件。
2. 再启动 RDK 主站。
3. 等 RDK 打印 `Cyclic exchange started.`
4. 然后再用 Jetson 发包。

## 6. 当前已知关键修复点

如果你以后重构代码，下面这些点不要随便删。

### 6.1 `wait_for_op_with_pdo()`

没有它，设备可能无法稳定从 `SAFE-OP` 进 `OP`。

### 6.2 `gateway_tsn_init_mm2s_dma()`

没有它，`ECAT->TSN` 很容易回到之前的 DMA 发送失败状态。

### 6.3 `gateway_tsn_force_1000m()`

这一步来自 full-port 例程的稳定配置经验，删除后 port1 链路状态可能变得不稳定。

### 6.4 最小帧补齐

删除后小 payload 帧可能发不稳定。

## 7. 推荐排障顺序

如果后面再出问题，建议按下面顺序查。

1. 先看固件是否打印 `ESC hardware OK` 和 `PDO: 60 bytes in, 60 bytes out`
2. 再看 RDK 是否能到 `OP`
3. 再看固件是否出现 `APPL_StartOutputHandler`
4. 再看 `E2T/T2E/TXF`
5. 再分别用 Jetson 收包和发包单独验证两个方向

不要一开始就只看 `tcpdump`。这个工程里，很多问题在 DMA 初始化、端口模式和 PDO 时序层面，链路有时候并不是第一故障点。
